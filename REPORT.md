## 3. Модель

`Match` — базовий клас: `__init__` перевіряє спільні інваріанти (непорожні
назви команд і дата, невід'ємний рахунок), а поле `round` — через
`@property`/`@round.setter`, що відхиляє значення менше 1:

```python
@property
def round(self) -> int:
    return self._round

@round.setter
def round(self, value: int) -> None:
    if value < 1:
        raise ValueError("тур має бути не менше 1")
    self._round = value
```

Спеціальні методи: `__str__` — коротке читабельне подання (`"Динамо 2:1
Шахтар (тур 1, група)"`), `__repr__` — діагностичне, з іменем фактичного
підтипу через `type(self).__name__`, `__eq__` — порівнює `type(self) is
type(other)` і всі поля, повертає `NotImplemented` для несумісного типу
(тому `match == 42` не падає, а коректно дає `False`). Впорядкування — не
окремий `__lt__`, а `key=` при сортуванні (`analysis.build_standings`
сортує за `(-points, -goal_difference, team)`), як рекомендує методика.

## 4. Dataclass

```python
@dataclass(frozen=True)
class TeamStanding:
    team: str
    played: int
    points: int
    goal_difference: int
```

Одна команда — один незмінний рядок турнірної таблиці. `frozen=True`
забороняє змінити результат після обчислення; усі поля — примітивні
значення, тому немає ризику змінюваного стану, що впливає на рівність.

## 5. Підтипи та протокол

`GroupMatch` (нічия дозволена, `points()` → 3 очки за перемогу, 1 за нічию,
0 за поразку) і `PlayoffMatch` (нічия заборонена власним інваріантом у
конструкторі — `"матч плей-офф не може закінчитися нічиєю"`, `points()` →
переможець 2, переможений 0) — спільна операція `points()`, різні формули.

```python
class PointsEarning(Protocol):
    home: str
    away: str
    home_score: int
    away_score: int
    def points(self) -> tuple[int, int]: ...
```

`analysis.build_standings(matches: Iterable[PointsEarning])` викликає лише
`match.points()` і атрибути полів — жодного `isinstance`/`if` за конкретним
підтипом. Тест `test_build_standings_works_polymorphically_across_subtypes`
передає список із `GroupMatch` і `PlayoffMatch` разом і перевіряє коректний
результат для обох.

## 12. Відповіді на контрольні питання

1. Клас описує структуру й поведінку (шаблон); екземпляр — конкретний
  об'єкт із власним станом, створений за цим шаблоном.
2. `__init__` виконується одразу після створення екземпляра й установлює
  початкові значення атрибутів; `self` — явне посилання на поточний
  екземпляр, перший параметр кожного методу.
3. `@property` дає змогу звертатися до методу як до звичайного поля під
  час читання чи запису, що дозволяє приховати перевірку значення за
  знайомим синтаксисом `obj.field`.
4. Setter записує у внутрішнє поле (наприклад, `self._round`), а не в саму
  властивість (`self.round`) — інакше виклик `self.round = value`
  рекурсивно викликав би той самий setter і призвів до нескінченної
  рекурсії.
5. `@dataclass` автоматично додає `__init__`, `__repr__`, `__eq__` та інші
  типові методи класу даних за оголошеними полями.
6. `frozen=True` забороняє змінювати поля після створення екземпляра,
  роблячи намір незмінності явним і захищеним на рівні мови.
7. `__str__` повертає подання для читача (використовується `print`/`str`);
  `__repr__` — діагностичне подання для розробника (використовується в
  консолі й налагодженні).
8. `__eq__` має повертати `NotImplemented` (не `False` і не виняток) для
  несумісного типу, щоб Python міг спробувати симетричний варіант
  порівняння в іншого об'єкта.
9. Сортування через `key=` простіше, коли критерій порівняння не є сталою
  властивістю об'єкта або потрібен лише в одному конкретному місці — повний
  набір методів порівняння (`__lt__` тощо) виправданий, якщо об'єкти
  порівнюються всюди за одним природним порядком.
10. `super()` звертається до наступної реалізації в порядку розв'язання
   методів (MRO) — у простій ієрархії це означає виклик ініціалізації
   базового класу з підтипу.
11. MRO (Method Resolution Order) — порядок, у якому Python шукає метод
   серед класів ієрархії; його потрібно враховувати при множинному
   успадкуванні, щоб знати, яка саме реалізація виконається.
12. Качина типізація означає, що важливо лише те, які методи/атрибути має
   об'єкт, а не до якого класу він формально належить («якщо крякає, як
   качка, — це качка»).
13. `Protocol` розв'язує проблему опису спільної поведінки без
   успадкування від спільного базового класу — структурна типізація
   перевіряє наявність потрібних методів/атрибутів, а не ієрархію класів.
14. `analysis` не повинен перевіряти кожен конкретний підтип, бо тоді
   довелось би дублювати ту саму логіку вибору поведінки і в підтипі
   (`points()`), і в `analysis` (`if isinstance(...)`) — будь-яка зміна
   вимагала б синхронізувати обидва місця.
15. Перетворення словника на об'єкт має виконуватися в `loader`
   (`build_match`), на межі завантаження — так `analysis` отримує лише
   вже перевірені, готові об'єкти.
16. Модулі не повинні запускати код під час імпорту, бо інакше тест,
   написаний як `from kzp_lab07.cli import main`, мимовільно запустив би
   CLI лише через сам факт імпорту — захист `if __name__ == "__main__":`
   виконує код лише при прямому запуску файлу.
17. Тестами перевіряються: відхилення setter-ом неправильного значення,
   незмінність `frozen`-dataclass, рівність і нерівність об'єктів (зокрема
   різних підтипів з однаковими полями), різні результати `points()` у
   підтипів, робота спільної функції без перевірки конкретного класу.
18. `pytest` перевіряє поведінку, `ruff` — стиль і типові помилки коду,
   `wheel` підтверджує, що пакет можна встановити й запустити окремо від
   робочого дерева розробника.
19. Тестовий набір має містити: коректні об'єкти обох підтипів, дубльовані
   значення (рівні об'єкти), межове значення властивості (`round=1`),
   помилковий рядок CSV (нечислове поле, невідомий `kind`, нічия в
   плей-офф) і порожній вхід.
20. У REPORT декларуються: порівняння словникової й об'єктної моделей,
   опис базового класу й властивостей, підтипи й протокол, dataclass,
   структура модулів, результати тестів, доказ еквівалентності звітів і
   результати CI на трьох ОС.
